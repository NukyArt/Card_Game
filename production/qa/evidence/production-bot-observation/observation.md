Дата: 2026-11-14. История: `production/epics/ally-bots/story-002-production-contribution.md`.

## Конфигурация и запуск

Обычная соло-конфигурация из `core/src/main/resources/data/`: один человек, три бота, нормальная сложность, без изменения данных карт, проекта, рынка или баланса. Seed 0. Человек пасует на рынке и в производстве. Окно 1280×720, захват после 60 отрисованных кадров каждого состояния.

```sh
JAVA_TOOL_OPTIONS='-Dmarket.observation.unattended=true -Dmarket.observation.seed=0' \
  ./gradlew :desktop:run --no-daemon
```

Последний запуск после исправления ротации очереди: exit 0. Экран показывает последовательное воспроизведение неизменяемых `GameSessionCommandResult.snapshot()` после синхронного выполнения команд. Это не живое пошаговое выполнение с паузой; надпись на экране явно обозначает это ограничение.

## Дополнительные исполняемые проверки

Java 17 JShell, classpath: `core/build/classes/java/main`, `core/build/resources/main`, локальный `gdx-1.14.2.jar`. На Windows передано `MSYS_NO_PATHCONV=1`. Проверки выводили PASS и завершились exit 0; при нарушении проверяемого условия сценарии выбрасывали исключение и вызывали System.exit(1). Первые подготовительные попытки имели ошибку classpath и ошибки синтаксиса JShell; они не считались проверками, исправленные сценарии выполнены отдельно.

Проверено на сессиях, построенных из реального каталога и небольших синтетических требований этапов:

- Все 20 баз каталога активируются через `ProductionBotController`, все команды приняты, очередь переходит следующему боту.
- Случайные выплаты Цитадели при источнике `bound -> 0` разрешают ожидающее распределение золота до следующего действия.
- Базовая выплата Лаборатории завершает первый этап с потребностью в двух свитках; обмен выбирает стройматериал уже для следующего этапа, списывает 2 золота. Итоговый баланс 8 из начальных 10.
- Две базы без улучшений передаются в этап с требованием двух карт; удаление первой не пропускает вторую из-за сдвига индекса.
- Произведённое золото завершает первый этап, финальный взнос личного золота продолжает последовательно второй и третий; ранние части алгоритма не перезапускаются.
- Когда ресурсы не нужны, Шахта выбирает золото, обязательный выбор Ростовщика — первый разрешённый ресурс из данных, необязательный обмен пропускается.
- Изменение исходной карты требований не меняет уже созданный decision context.

Вывод итоговых проверок:

```text
PASS: exchange targets new stage after base payout
PASS: card donations handle shifted indices
PASS: repeated gold across stages
SMOKE PROBES PASSED
PASS: mine gold fallback, mandatory first allowed fallback, optional exchange skip, immutable decision context
```

## Риск требования карт и ротация очереди

Отдельно выполнен невизуальный JShell-прогон обычной соло-конфигурации с seed 0 до исхода партии. Человек только пасует; боты выполняются через `SoloGameController`; фазы завершаются штатными командами. Это проверка командного пути, не визуальная проверка всей партии и не полноценный playtest. Запуск использует существующую реализацию фаз без добавления ручных доходов или иных правил.

- Все 30 раундов прошли без отклонённых команд и зацикливания очереди.
- Проверена ротация первого участника: player → bot-1 → bot-2 → bot-3.
- Раунд 5: walls-workshops, переданы требуемые 3 карты.
- Раунд 14: city-district.
- Раунд 27: mage-tower, передано 5 карт из 6.
- Раунд 28: mage-tower, переданы все 6 карт.
- Раунд 30: DEFEAT по лимиту раундов, проект остался на mage-tower.

```text
PASS: deterministic normal setup, human passes, all rotated queues terminate without rejection; outcome=DEFEAT round=30
```

В этом конкретном раскладе блокировки на картах не возникло. Это не доказательство её отсутствия при других раскладах или одних только базах с улучшениями, не оценка баланса и не доказательство достижимости победы. Правило не отдавать базы с улучшениями и рыночная стратегия не изменялись.

## Границы и совместимость

- Старый двухаргументный `SoloGameController` остаётся market-only; конструктор с RandomSource и `SoloSessionBuilder.buildController` автоматизируют обе фазы.
- Существующие конструкторы активации и прямой вызов resolver сохранены.
- Диагностический экран расширен по отдельному разрешению; обычный UI, таймер и пауза не реализовывались в этой истории.
- Новых вызовов API libGDX не добавлено; использован существующий framebuffer-захват.
- История остаётся In Progress до отдельного `/story-done`.
